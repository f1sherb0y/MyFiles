# MyFiles 的设计

MyFiles 是用 [MyGo](https://github.com/egoist/mygo) 原生界面写的文件管理器，目标是在 Windows 上替代资源管理器：进文件夹要快，界面要紧凑，标签页能拖成上下左右的分屏。

这篇说它由哪些部分组成、每部分为什么这样做，以及从 Explorer++ 学了什么、没照搬什么。

## 分层

```
cmd/myfiles            入口：解析命令行，--help / --set-default 在这里答完就退出
internal/cli         命令行：MyFiles 自己的选项 + explorer.exe 的参数
internal/app         界面：窗口、分屏、标签、地址栏、各种视图、快捷键（全平台同一份）
internal/workspace   分屏布局：一棵二叉树，叶子是放标签的窗格（纯数据，不知道界面）
internal/config      设置和上次的会话（JSON，写在用户配置目录）
internal/fsys        文件系统：读目录、排序、路径、盘符、常用文件夹
internal/shell       桌面环境：图标、类型名、打开、复制/移动/删除、系统右键菜单、注册为默认文件管理器
internal/watch       监视文件夹的变化：每个盘一个监视，不占着文件夹
internal/clock       高精度计时（测量用）
third_party/mygo     MyGo，带少量补丁（见 patches/mygo.patch）
```

依赖只往下走：`app` 用 `workspace`、`config`、`fsys`、`shell`、`watch`；后五个互不依赖界面。

### 平台边界

和操作系统打交道的代码只在两个包里，各自用文件名后缀分开：

| 包 | Windows | 其他系统 |
|---|---|---|
| `fsys` | `list_windows.go`（一次系统调用拿到整个目录）、`path_windows.go`、`sortkey_windows.go`、`volumes_windows.go` | `fsys_other.go`：标准库实现，能编译、能跑 |
| `shell` | `*_windows.go`：COM / Win32，全部用 `syscall`，没有 cgo | `shell_other.go`：返回 `ErrUnsupported` 的桩 |

`shell/shell.go` 是这个包对外的全部接口，注释就是规格。移植到 macOS 时要做的是：给 `shell` 写一组 `*_darwin.go`（NSWorkspace 取图标、NSFileManager / Finder 做文件操作、废纸篓），需要的话给 `fsys` 写 `list_darwin.go`（`getattrlistbulk`）；`app`、`workspace`、`cli`、`config` 不用动。`GOOS=darwin go build ./...` 现在就能过，CI 里可以一直保持。

`app` 里还有一层小接口 `desktop`（`desktop.go`）：剪贴板、打开文件、系统菜单、属性页都经过它。正式运行时它转给 MyGo 和 `shell`；测试里换成只记录的假实现，所以测试不会在桌面上弹任何东西。

## 进文件夹为什么快

一次导航从按键到出画面经过这几步，每步的做法：

1. **读目录**（`fsys.List`）。打开目录句柄，用 `GetFileInformationByHandleEx(FileFullDirectoryInfo)` 配 256 KB 缓冲区，一次调用拿回几千项的名字、大小、时间、属性。这些都在目录索引里，不打开任何文件。名字从 UTF‑16 转 UTF‑8 时一个缓冲区只分配一次。System32（5,029 项）约 1.6 ms，WinSxS（26,254 项）约 21 ms。
2. **排序**（`fsys.Sort`）。先给每个名字算一次排序键（`LCMapStringEx`，数字按数值、忽略大小写、按用户语言，结果和资源管理器的顺序一致），多核并行算；之后比较就是比字节串。排的是下标数组，条目本身不动。5,029 项约 0.5 ms。
3. **等结果**（`navigate`）。读目录在另一个 goroutine 里做，主线程最多等 40 ms。本地磁盘远用不了这么久，所以文件夹在触发导航的那一帧里就画出来，不会先画一帧旧内容。超过 40 ms（网络盘、休眠的硬盘）就不等了，结果回来再刷新，窗口不卡。
4. **构建界面**。表格和网格都只构建可见的行（MyGo 的虚拟列表），所以 26,000 项和 50 项的构建时间一样。每行的日期、大小只在第一次滚进视野时格式化一次。
5. **图标和类型名**（`app/icons.go`）。在 3 个工作线程上向系统取，后请求的先做（那是用户正在看的）。普通文件按扩展名缓存，取的时候不碰磁盘；只有 exe、lnk、ico 这类自带图标的才按路径取。

MyGo 的补丁里有两处是为这条路径加的：`Context.Rebuild`（一帧内状态变了再构建一遍，而不是等下一帧）和 `Context.OnPresented`（这一帧交给显示之后回调，用来计时）。

### 第一帧就是最终的画面

新文件夹的第一帧如果和下一帧不一样，眼睛看到的就是「闪一下」。2026-11-12 查到三处会这样，都改掉了；`TestFolderShowsAtOnce` 在六种视图里逐像素比较「导航后的第一帧」和「稳定后的画面」，除状态栏的耗时数字外必须相同，新标签也一样。

- **网格的列数**（最明显的一处）。MyFiles 每进一个文件夹换一个新的 `GridState`，而 MyGo 的网格在状态不知道宽度时按**窗口**的宽度算列数，下一帧才按真实宽度重排，于是列表、图标视图里每次进文件夹内容都先多排几列再跳回来。补丁：状态是新的就用元素上一帧的宽度，元素也是新的（新标签）就用最近一层上一帧在的祖先的宽度。
- **图标和类型名的占位**。原来第一帧画通用图标和按扩展名猜的英文类型名（`TXT File`），真的到了再换。现在：
  - 按扩展名的类型名和图标存在磁盘上（`app/iconstore.go`，`%LOCALAPPDATA%\MyFiles\types.json` 和 `icons-<像素>.bin`，`MYFILES_CACHE_DIR` 可以换位置），启动时读进来，见过的类型第一帧就是对的。第一次用到某个类型时仍在后台向系统核对一次，一样就什么都不动，不一样才替换并重写文件。只存 128 像素以内的尺寸，每个文件最多 4,000 个类型。
  - 系统的大图标不管要多大都是 256 像素。工作线程把它缩到视图实际显示的像素（`icons.fit`）再用：省内存，而且每次运行得到的像素相同，磁盘上的和系统刚给的才能比较。
  - 不知道的（没见过的类型、exe 之类自带的图标）：文件夹读完后，主线程为第一屏要用的那些最多等 10 ms（`icons.await`，`iconWait`），等到的直接进第一帧；没等到的照旧先画占位、到了再换。只有正在显示的标签才等。
  - 类型名在系统回答之前留空，不再猜：填上比换掉不显眼。
- **地址栏**。放不下时收进「…」的级数按地址栏上一帧的宽度算，原来这个宽度记在标签上，新标签第一帧没有，会先全画出来再收。现在取的是窗格里地址栏这个元素上一帧的宽度，和哪个标签无关。

### 尺寸变了的那一帧

上面三处是同一类问题的入口，根因在 MyGo 的帧结构：先构建、后排版，而有些东西构建时就要知道宽度（网格一行放几个、地址栏收起哪几级），只能用上一帧的。宽度一变（分屏、拖分割线、改窗口大小、开关侧栏），这一帧就按旧宽度画出来，下一帧才对，看到的是抖一下；连续拖动时每帧都抖。2026-11-12 实测：分屏、改窗口大小后恰好有 1 帧不对，列表和图标视图是整个内容区，详细信息视图是地址栏。

补丁治的是这一类（`ui/runtime.go` 的 `sizesStale`）：构建时凡是读过上一帧尺寸的元素（`Element.Bounds`、`LayoutBounds`）都记下来；排版后如果其中有元素的尺寸变了，或者网格发现列数不对，就把新尺寸写回去，在同一帧里重新构建、重新排版，然后才画，最多重来两次。尺寸没变的帧不受影响。`TestNoFrameOfTheOldSize` 在六种视图里对分屏、改窗口大小、关侧栏、新标签、设置标签逐帧比较，要求每一帧都和稳定后的画面相同；把重建关掉，42 个用例里 30 个失败。

没改的：缩略图（图片、视频、PDF）仍然是之后补上的，取一张可能要几十毫秒；应用启动后的第一帧、新分出来的窗格的第一帧，网格还是可能先按窗口宽度排一次。

### 和 Explorer++ 的差别

读 Explorer++ 源码（`ShellBrowser/`）得到的结论，和 MyFiles 的取舍：

| | Explorer++ | MyFiles |
|---|---|---|
| 枚举 | `IShellFolder::EnumObjects`，默认在界面线程上，逐项取 pidl | 直接读文件系统目录，一次调用一批，在后台线程 |
| 每项信息 | 每项 3 次 `GetDisplayNameOf` + `GetAttributesOf` + `SHGetDataFromIDList` | 枚举时已经带回来了 |
| 列表 | 非虚拟的 ListView，每项 `InsertItem` | 虚拟列表，只建可见行 |
| 排序 | 比较函数里每次克隆 pidl、`StrCmpLogicalW` | 预先算好排序键，比较字节 |
| 图标 | 按完整路径缓存，先进先出 | 按扩展名缓存，后进先出 |
| 变更通知 | 每条通知整表重排 | 去抖后整个文件夹重读一遍（读一遍只要 1 ms 左右） |

代价也在这里：MyFiles 只显示文件系统里的文件夹。控制面板这类不是目录的 shell 位置，MyFiles 自己不显示，命令行里遇到就交还给资源管理器。例外是回收站，它是单独做的，见[回收站](#回收站)。

沿用 Explorer++ 的：导航带代数（generation），旧导航的结果回来直接丢掉；来不及的图标先出占位再换；文件操作全部走 `IFileOperation`，进度、冲突询问、回收站、撤销都是系统的；「设为默认文件管理器」写的注册表位置。

## 分屏和标签

`workspace.Layout` 是一棵二叉树：内部节点是一次分割（左右或上下，带比例），叶子是窗格，窗格里是一排标签。操作只有几个：`AddTab`、`RemoveTab`、`MoveTab`（同窗格内就是换位置）、`Split(目标窗格, 标签, 上/下/左/右/中)`。窗格里最后一个标签走了，窗格自动合并回相邻的。整个结构能直接序列化成 JSON，会话恢复就是把它读回来。

界面上（`app/strip.go`、`app/view.go`）：

- 拖标签到另一个标签上：插到它前面或后面（看落在哪一半）。
- 拖到窗格内容区：按落点分五个区，四边各占 25% 表示在那一侧分屏，中间表示并入这个窗格；拖动时用半透明色块预览结果。
- 拖文件悬停在标签上 0.6 秒，标签自动切过来（方便往它的子文件夹里放）。
- 分割线可拖，双击回到一半。

设置也是一个标签页（`Tab.settings`，内容在 `app/dialogs.go` 的 `settingsPage`）：Ctrl+, 或右上角的按钮打开，一个窗口只有一个，再按就切过去；可以像别的标签一样拖动、分屏、关闭。它没有文件夹，所以不显示工具栏和状态栏，文件夹的快捷键对它不起作用；会话里它的路径记成 `::settings`。

## 标签之间的同步

标签之间不共享状态：每个标签监视自己显示的文件夹，有变化就重读，重读时保留选择和滚动位置。两个标签开同一个文件夹，各自收到同一个变化，各自重读。MyFiles 自己做的删除、移动、新建，做完还会让相关的标签立刻重读，不等通知。

**监视不能占着文件夹。** 通常的做法是每个文件夹开一个句柄用 `ReadDirectoryChangesW`，MyFiles 原来也是。但 Windows 的规则是：一个目录的子孙里有打开的句柄，这个目录就不能改名。于是只要有标签开在 `D:\a\b\c`，`D:\a` 和 `D:\a\b` 就改不了名、移不走、删不进回收站（删进回收站也是一次改名），对任何程序都是这样。资源管理器也有这个问题：它的窗口开在子文件夹里时，普通程序改上级的名同样被拒绝，只有走 shell 的操作才会先让它松手。

试过的另一条路是 shell 的变更通知（`SHChangeNotifyRegister`），实测不行：带文件系统级通知时延迟约 1 秒，而且 shell 在进程里替你开了同样的句柄，照样挡改名，被监视的文件夹自己改名、被删也没有通知；只收 shell 级通知时，普通程序做的改动一个都收不到。

现在的做法（`internal/watch`）：**每个盘只开一个句柄，开在盘的根目录上，递归监视整个盘**，再按路径把事件分给标签。根目录不会被改名，所以不挡任何东西。

- **分发**：事件带相对于盘根的路径。是某个标签的文件夹的直接子项，就是「内容变了」（80 ms 没有新事件，或最迟 400 ms，通知一次）；是这个文件夹自己或它的某个上级被改名，事件里有新旧名字，标签直接跟到新路径（`Window.follow`：保留选择和滚动位置，前进后退的历史里的路径也一起改）；是它或上级被删、被移走，标签重读、读不到，就退到最近还存在的上级。更深的子孙的变化不管。
- **比较不分配内存**：整个盘的每个事件都会到这里，绝大多数不属于任何标签，所以比较是在 UTF‑16 上逐字符做的大小写不敏感前缀比较，不生成字符串。
- **洪峰**：别的程序疯狂写盘时（`npm install`、编译内核），一个盘每秒超过 2000 个事件就切到粗略模式：每 250 ms 才读一次，多出来的事件让内核自己丢掉（缓冲区溢出），这时不知道具体改了什么，就只看被监视的文件夹的修改时间，变了才通知。降到每秒 500 个以下回到精确模式，并补一次通知（修改时间看不出文件大小的变化）。普通的溢出也按「可能变了」处理。
- **链接**：监视前先把路径解析成真实路径（`GetFinalPathNameByHandle`），经过联接点、`subst` 盘的文件夹按它真实所在的盘和路径匹配。这种文件夹被改名时没法反推出显示的路径，就当作没了，标签重读。
- **不归它管的**：网络路径、WSL、可移动盘（根目录上的句柄会妨碍安全弹出）仍然逐个文件夹监视，那里上级改名被挡的问题还在。
- 一个盘上最后一个标签离开 2 秒后关掉这个盘的监视。

实测（这台机器，2026‑11‑12）：

| | 逐文件夹监视 | shell 通知 | 每个盘监视根目录 |
|---|---|---|---|
| 普通程序的改动多久收到 | 即时 | 约 1 秒 | 即时 |
| 上级文件夹改名 | 被拒绝 | 被拒绝 | 可以 |
| 被显示的文件夹改名 | 不知道新名字 | 没有通知 | 带新旧名字 |

事件量：D: 空闲 10 秒 2 个，C: 空闲 20 秒 38 个，C: 上 40 秒的 Go 测试加完整重编译 7160 个。压力测试是 8 个线程尽快写 20 万个 2 KB 的文件再删掉（每秒约 2 万个事件）：写入速度不受影响（约 14000 个/秒）；逐个读事件要用掉一个核的 14%，加了洪峰模式之后整个过程是 0.22 秒的 CPU，不到一个核的 1%，期间被监视的文件夹里新建的文件照常被发现。探针程序在 `out\shcn\`（不入库）。

## 侧栏

`app/sidebar.go` 画，`app/places.go` 管状态（所有窗口共用），系统那一侧在 `shell/places_windows.go`。从上到下：

- **固定的文件夹**（`Settings.Pinned`）。显示成两组：每个用户都有的（桌面、下载、文档、图片、音乐、视频这些已知文件夹，和回收站）不带标题放在最上面；用户自己固定的放在「收藏」标题下。拖动换位置只在各自的组里。第一次运行时从资源管理器的快速访问导入：枚举 `shell:::{3936E9E4-…}`，逐项建它的右键菜单，有「取消固定」命令的就是固定的（约 0.1–0.2 秒一项，在后台做，这台机器 12 项用了 2.2 秒）。之后就是自己的：文件夹的右键菜单或侧栏行的右键菜单可以固定、取消，拖动换位置。导入完成前先放用户的几个已知文件夹和回收站。
- **最近**。每进一个文件夹记一次（`recent.json`，路径、次数、最后时间，最多 200 个），按「次数 ÷（1 + 距今天数）」排，显示前 4 个没被固定的。盘符根目录不记，树里已经有。快速访问里它自己列的常用文件夹作为初始值。
- **树**。此电脑、网络、Linux 三个根，每个节点点箭头才读它下面的文件夹（`readKids`，后台读），展开状态存在 `Settings.Expanded`。标签页读某个文件夹时顺手更新树里这个节点（`listed`），每次刷新侧栏（15 秒）也重读展开的节点。一个节点最多列 500 个子文件夹。
  - 网络：`WNetEnumResource` 列附近的电脑，`NetShareEnum` 列一台电脑的共享；电脑本身（`\\NAME`）不是文件夹，点了只是展开。
  - Linux：注册表 `HKCU\…\Lxss` 里的发行版，路径是 `\\wsl.localhost\<名字>\`，就是普通目录。发行版没在运行时第一次进要等它启动（实测 2.5 秒）。
- **回收站**不是文件系统里的目录，但在标签里像文件夹一样显示，见[回收站](#回收站)。WPS 云盘、图库、主文件夹这类虚拟位置不做。

名字和图标跟资源管理器一致：

- 名字用系统的显示名（`SHGetFileInfo` 的 `SHGFI_DISPLAYNAME`），所以「桌面」「文档」是中文，而挪到 D 盘、没有 desktop.ini 的 Downloads 还是 Downloads。
- 已知文件夹（下载、图片、音乐、视频……）的图标按「已知文件夹」取：`IKnownFolderManager::FindFolderFromPath` 找到定义，用定义里的图标。不靠 desktop.ini，因为系统只对带只读属性的文件夹读它，挪过位置的文件夹往往没有。
- 回收站、此电脑、网络、Linux 是系统命名空间里的位置（`::{CLSID}`），名字和图标按 pidl 取。

## 地址栏

`app/address.go`。平时每一级路径是一个按钮，点了直接去那一级（并选中刚才所在的子文件夹）；中键点在新标签里打开；文件也可以直接拖到某一级上。放不下时前面的几级收进「…」菜单。

点按钮右边的空白、按 Ctrl+L / Alt+D / F4，地址栏变成输入框，整条路径选中，可以直接复制、粘贴、输入。输入框接受的东西和命令行一样（`cli.Locate`）：绝对路径、相对当前文件夹的路径、`%USERPROFILE%`、`~`、`shell:Downloads`、`file:///`；输入的是文件就进它的文件夹并选中它。

## 视图

每个标签有自己的视图，新标签沿用上次选的，会话里按标签保存。Ctrl+Shift+1…6、Ctrl+滚轮或工具栏最右的按钮切换：

| 视图 | 实现 | 图标 |
|---|---|---|
| 详细信息 | `ui.Table`：列可排序、调宽、换位置 | 16 |
| 列表 | `ui.GridView`：只有名字，多列 | 16 |
| 平铺 | 同上：图标旁边是名字、类型、大小 | 32 |
| 中 / 大 / 超大图标 | 同上：图标在上，名字在下，最多两行 | 48 / 96 / 192 |

图标按视图需要的像素取系统里「不小于它」的那一档再缩小，不放大。三个图标视图里，图片、视频、PDF 用内容的缩略图代替图标（`shell.Thumbnail`，走系统的缩略图缓存），在单独的两个工作线程上做，不挡图标；云端占位文件不取，免得触发下载。选择、光标、右键菜单、拖放、重命名在所有视图里是同一套状态（`Tab.sel`、`Tab.cursor`），切视图不丢选择。

## 语言

用的是 MyGo 自带的多语言机制，没有自己造：

- 消息目录在 `cmd/myfiles/locales/`，一种语言一个 JSON（ICU MessageFormat，带复数规则）：`en.json` 是源语言，`zh-Hans.json` 是简体中文。目录必须在 `mygo.json` 所在的项目目录里。
- `mygo generate`（`mygo build` 也会做）从目录生成 `catalog_gen.go`，每条消息一个带类型的函数，界面代码里写 `locales.MenuOpen()`、`locales.StatusSelected(n)`。生成的文件要提交，这样 `go build`、`go test` 不依赖 CLI。改了 JSON 之后在 `third_party\mygo` 里跑 `go run .\cmd\mygo generate ..\..\cmd\myfiles`。
- 显示哪种语言由 MyGo 决定：按系统的首选语言列表，在程序有的语言里挑最合适的（`zh-CN`、`zh-SG` 得到简体中文），都不合适就用英文。设置里的「语言」可以改成固定某一种，选择存在用户数据目录的 `locale` 文件里；`MYGO_LOCALE=zh-Hans` 可以只对一次运行生效。
- MyGo 自己控件的文字（输入框的右键菜单、对话框按钮等）跟着同一种语言，简体中文的翻译由生成的代码自动引入。
- 表格的列标题、视图名称是每帧按当前语言取的，切换语言立即生效，不用重启。
- 加一种语言：在 `locales/` 里放一个 `<标签>.json`，重新生成即可；`mygo i18n check` 会报缺的键和写错的占位符。

没翻译的：命令行的帮助文字；注册到系统右键菜单里的「Open in MyFiles」；侧栏里「下载」「桌面」这些文件夹显示的是磁盘上的真实名字，不是系统的本地化名字。文件类型名（「文本文档」）、More 菜单里的项本来就是系统给的，一直跟系统语言走。

## 自动更新

用的是 MyGo 的 `mygo.Updater`（签名的更新包，发布在 GitHub Releases），界面是自己的（`app/update.go`）：

- 启动时就检查一次（在另一个线程上，不耽误启动），之后每 6 小时一次。只在正常运行的实例里做，基准、截图这类模式不查。
- 发现新版就在后台下载、验签、替换安装目录里的文件，期间什么都不显示；正在运行的程序不受影响。
- 换好之后出现「重启以更新」按钮：有侧栏时在左上角「MyFiles」的右边，没有侧栏时在左下角那个窗格的状态栏里。点了先保存会话再重启，标签页会恢复。
- 设置里的「自动检查更新」可以关；离线、请求失败都不提示，等下一次。
- 密钥：公钥写在 `cmd/myfiles/mygo.json` 的 `updates.publicKey` 里，编进程序；私钥在本机的 `%APPDATA%\mygo\update-keys-myfiles\mygo-update.key`，**不进仓库**。已安装的程序只接受这把私钥签过的更新，丢了就再也推不了更新，泄露了别人就能给用户推代码。发布工作流从仓库的 secret `MYGO_UPDATER_PRIVATE_KEY` 读它，没有就失败。
- 发布时除了安装包还要上传 `update-windows-amd64.json`（清单，程序从最新 release 读它）、`myfiles-<版本>-windows-amd64.tar.gz` 和增量包 `*.delta`，`release.yml` 已经这样做。
- 本地试一遍完整流程不用发布：`out\try-update.ps1` 的做法是构建一个旧版和一个 0.9.0，设 `MYFILES_UPDATE_DIR=<新版构建输出的目录>` 运行旧版（加 `--ephemeral`），它会从这个目录读清单和更新包，验签照常。2026-11-12 这样验证过：16 秒内目录里出现了 0.9.0 的 `MyFiles.exe`，按钮出现在左下角。按钮的点击只在无窗口测试里验证过。
- 只有用安装包装的那份会更新（要能写自己的安装目录）；`go build` 出来的开发版 `Updater.Enabled()` 是 false。

`app/band.go`。在视图的空白处按下：取消选择（按着 Ctrl 或 Shift 则保留）；拖动超过 4 DIP 就画一个框，碰到的条目被选中，框缩回去时再放开，视图滚动时框的起点跟着条目走。视图元素的输入回调也会收到落在条目上的按下，所以每帧记下各条目的位置（`Tab.entryBoxes`），落在条目上的不管，那是条目自己的点击和拖放。详细信息视图里每一行占满整宽，空白只有行下面那一块。

## 文件的复制、剪切、拖放

- **剪贴板**用系统的格式：`CF_HDROP` 文件列表 + `Preferred DropEffect`（2 = 剪切，5 = 复制）。所以在 MyFiles 里剪切的文件能粘贴到资源管理器，反过来也一样。剪切的文件图标变淡，粘贴一次后失效；剪贴板被别的内容顶掉时也恢复。
- **拖放**是系统级的（OLE）：行可以拖到别的窗格、别的 MyFiles 窗口、别的程序；别的程序拖进来的文件同样接收。落点可以是文件夹那一行、窗格空白处、标签、地址栏的某一级、侧栏的位置。
- **移动还是复制**和资源管理器一样：同一个卷默认移动，跨卷默认复制；按住 Ctrl 强制复制，Shift 强制移动。
- 真正搬文件的是 `shell.Copy / Move / Delete`，也就是系统的 `IFileOperation`：进度窗口、重名询问、回收站、Ctrl+Z 撤销记录都是系统的。同目录复制自动改名为「xxx - 副本」。

## 回收站

回收站在标签里像文件夹一样打开（侧栏、`shell:RecycleBinFolder`、地址栏输入都行），路径是它的 CLSID `::{645FF040-…}`。

- **读**：不走 shell 命名空间（那边一毫秒只列得出几项），直接读文件。每个盘的 `X:\$Recycle.Bin\<用户的 SID>\` 里，被删的东西改名成 `$Rxxxxxx.ext`，旁边一个 `$Ixxxxxx.ext` 记录：8 字节版本、大小、删除时间（FILETIME）、原路径（版本 1 是定长 260 个字符，版本 2 前面带长度）。把所有盘的记录读出来就是列表。这台机器 22 项，热的时候 3 ms。没有对应 `$R` 的记录是残留，跳过。
- **显示**：行的身份是 `$R` 路径（两个同名文件靠它区分），显示的是原名；列是名称、删除日期、原位置、大小；排序和过滤按这些字段，不按 `$R` 文件自己的。图标按扩展名取类型图标，不出缩略图。回收站的内容就是各盘 `$Recycle.Bin\<SID>\` 里的文件，开着回收站的标签监视这些文件夹（见[标签之间的同步](#标签之间的同步)），所以别的程序删除、还原、清空，这里也会自己更新；MyFiles 自己做完这些动作之后还会立刻重读一次。
- **动作**：只有还原、永久删除、清空、复制原路径。打开、复制、剪切、粘贴、重命名、新建、拖放、属性、系统菜单在这里都关掉。
  - 还原：`MoveFileEx` 把 `$R` 移回原路径（不带替换标志），原文件夹没了就先建；原位置已经有同名的就还原成「名字 (2)」，绝不覆盖；成功后删掉 `$I` 记录，重读显示着那个文件夹的标签。
  - 永久删除：删 `$R`（文件夹递归）和 `$I`，先问。只接受 `$Recycle.Bin` 里以 `$R` 开头的路径，别的一律拒绝。
  - 清空：`SHEmptyRecycleBinW`（不要它自己的确认、进度和声音），先由 MyFiles 自己问一次。
  - 之后都调 `SHUpdateRecycleBinIcon`，让桌面上的回收站图标跟着变。

## 没有声音

- 启动时 `CoInternetSetFeatureEnabled(FEATURE_DISABLE_NAVIGATION_SOUNDS)` 关掉导航的「咔哒」声。
- 窗口没有系统菜单栏，Alt+字母、F10 这类按键不再进系统的菜单循环（那是「叮」的来源）；这是给 MyGo 打的补丁。
- 右键菜单、确认对话框、设置都画在窗口里，不用系统的消息框。
- 打开文件失败（比如文件没了）不弹系统对话框，错误显示在状态栏。
- 代码里没有任何 `MessageBeep` / `PlaySound`。

系统自己的界面仍然是系统的：文件操作的冲突询问、「更多选项…」打开的系统右键菜单、属性页。

### 打开方式

右键菜单的「Open With」是子菜单（`shell/openwith_windows.go`）：`SHAssocEnumHandlers` 按扩展名列出系统推荐的程序，带图标，点了用 `IAssocHandler::Invoke` 打开。列表在菜单打开时在后台取，按扩展名缓存 30 秒。图标的位置由程序自己报：图标文件加序号的用 `SHDefExtractIcon`，商店应用报的是包里的资源名，用 `SHLoadIndirectString` 换成 PNG 文件再读。

最后一项「Choose Another App…」打开 MyFiles 自己的选择框（`app/chooser.go`），不用系统的。系统的选择框普通程序叫不出来，2026-11-12 在 Windows 11 26300 上试过的办法都不行：`ShellExecuteEx` 的 `openas` 动作 0.1 秒后返回成功但什么都不显示；`SHOpenWithDialog` 返回 0x80073D54（进程没有包标识）；直接启动 `OpenWith.exe <文件>`，进程同样以 0x80073D54 退出，只在任务栏闪一下图标。

双击（`Window.openFile`）也走同一个选择框，顺序是：

1. 用户在 MyFiles 里为这个扩展名选过程序（设置里的 `openWith`，扩展名 → 程序的 ID），就用它打开；程序已经不在了（`shell.OpenIn` 返回 `ErrChoose`）就忘掉这个选择，往下走。
2. 否则问系统的默认程序。`shell.Open` 先自己判断这个默认能不能用（`needsChoice`）：`AssocQueryString` 查到的可执行文件是 `OpenWith.exe`，说明系统会弹选择框；查不到可执行文件、默认的 ProgId 是 `AppX…`、而它的 `PackageId` 在当前用户的包列表（`HKCU\Software\Classes\Local Settings\…\AppModel\Repository\Packages`）里没有，说明默认指向一个已卸载的商店应用。这两种情况都返回 `ErrChoose`。不这样先判断的话，静默方式的 `ShellExecuteEx` 会返回成功而什么都不做。查不到可执行文件的其他情况（比如 `.lnk`）照常交给 `ShellExecuteEx`。
3. `ErrChoose` 时弹选择框：先列 `SHAssocEnumHandlers` 推荐的程序，「更多应用」再列全部（没有推荐的类型直接列全部，没有扩展名的文件按 `.` 查）。勾着「始终使用此应用」就把选择记进 `openWith`。从双击进来默认勾上，从菜单进来默认不勾。

这个选择只在 MyFiles 里生效，不改系统的默认应用。实测有一个附带效果：某个类型在系统里没有用户选择时，用 `IAssocHandler::Invoke` 打开过一次之后，`AssocQueryString` 对这个类型就直接解析到那个程序了（2026-11-12 `.psd` → MyImages，注册表里没有出现 `UserChoice`）。

这个流程用真实鼠标在真实窗口里验证过（`out/pickcheck.ps1`，2026-11-12）：双击 `.jpg`（默认指向已卸载的"照片"）和 `.psd` 都弹出选择框，点 MyImages 后 0.4 秒内打开；再双击另一个 `.jpg` 不再询问，直接打开。

### More 子菜单：自己画系统的右键菜单

右键菜单的「More」里是系统菜单的各项（`app/sysmenu.go`、`shell/menuitems_windows.go`）。做法：

- 右键菜单一打开，就在后台让系统生成它的菜单（`shell.LoadMenu`，不显示），读出每项的文字、图标、是否禁用、子菜单；到了再补进 More，之前显示「Loading…」。
- 系统的菜单对象必须在生成它的线程上用，所以每个菜单占一个宿主线程，直到关闭（`takeHost` / `giveHost`）。
- 子菜单是扩展在展开时才填的：第一次要某个子菜单时，替它发 `WM_INITMENUPOPUP` 再读。
- 去掉 MyFiles 自己已有的项（按命令名：open、openas、cut、copy、paste、delete、rename、properties、refresh）和多余的分隔线。
- 扩展自己画的项（owner-draw）不给文字，跳过；它们还能从最后一项「System Menu…」打开的原生菜单里用到。
- 同一批文件的菜单在 0.6 秒内再次打开会沿用上一次的；执行过命令后作废。
- 启动 1 秒后在后台对一个文件、一个文件夹、一个文件夹的空白处各生成一次并丢弃（`warmSystemMenu`），把扩展预先装进进程。

### 系统菜单为什么慢

时间花在系统生成菜单上（`IContextMenu::QueryContextMenu`，要加载所有注册的右键扩展）。2026-11-12 实测，同一个进程里：第一次给文件生成 1.0–1.1 秒，第一次给文件夹生成 0.4–0.6 秒，之后每种类型 0.08–0.14 秒（png 第一次 0.23 秒）。先生成过文件夹的，再给各种文件生成都在 0.09–0.12 秒。也就是慢的是进程里头一次加载扩展，和具体文件类型关系不大，所以启动后预热一次就够。

## 默认文件管理器

设置里两个开关，对应 `shell.SetDefaultFileManager`，都只写当前用户（HKCU），不需要管理员权限：

- **用 MyFiles 打开文件夹**：`HKCU\Software\Classes\Directory\shell` 和 `Drive\shell` 下加一个 `myfiles` 动词并设为默认。别的程序用系统默认方式打开一个文件夹、桌面上双击文件夹、`start D:\dir` 都会到 MyFiles。直接点名资源管理器的调用不走这个关联，仍然是资源管理器：`explorer.exe /select,…`，以及「在文件夹中显示并选中」用的 `SHOpenFolderAndSelectItems`。
- **Win+E 打开 MyFiles**：`HKCU\Software\Classes\CLSID\{52205fd8-5dfb-447d-801a-d0b52f2e83e1}\shell\opennewwindow\command`，带一个空的 `DelegateExecute`。

打开开关前会把原来的值记到 `HKCU\Software\MyFiles\DefaultBackup`，关掉时原样写回（包括「原来没有这个值」），所以如果之前把 Explorer++ 设成了默认，关掉 MyFiles 的开关后还是 Explorer++。命令行里 `myfiles --set-default` / `--unset-default` 做同样的事。

显式运行 `explorer.exe D:\dir` 仍然是资源管理器：那是直接启动它的程序，没有走「打开文件夹」的关联。
